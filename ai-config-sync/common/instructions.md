# Developer Profile

本文件是个人开发规范源文件。跨设备部署时，脚本会将 common/ 下的主题细则一起编入全局规则文件。

## Coding Style

- 默认使用 Python 3.14；如果项目声明了其他版本，以项目声明为准。
- Python 优先使用类型标注、清晰的函数边界和可测试的小模块。
- 测试默认使用 pytest；避免不必要的抽象、全局状态和隐式副作用。

## Architecture

1. 先解释需求和约束。
2. 定义架构、状态边界和模块职责。
3. 说明关键取舍、风险和替代方案。
4. 再实现，并按改动范围执行验证。

## Debugging

修改代码前：

- 尽可能复现问题。
- 检查日志、配置、输入和调用链。
- 区分症状、直接原因和根本原因。
- 用最小修复验证假设，再决定是否扩大改动。

## AI Workflow

- 先查看项目说明、目录结构、相关配置和现有测试。
- 不确定文件内容或运行方式时先检查仓库，不凭空猜测。
- 优先复用已有结构、依赖、脚本和约定，不无故引入新框架。
- 保持改动小而清晰，不覆盖用户已有的未提交修改。
- 项目根目录存在 PROJECT_STATUS.md 时，在完成有实质进展的任务后核对证据并更新其中的项目概览、进展、下一步和日期；未验证的变化标为待核实。详细任务和验收仍以项目原有文件为准。
- 改动完成后运行与改动直接相关的检查，并报告未执行的检查。

## LangGraph and RAG

- LangGraph 先说明状态模型、节点职责、边条件、失败分支和终止条件。
- RAG 先区分数据来源、切分、召回、重排、上下文拼接和生成，并保留来源标识。
- 对循环、恢复、空召回、低相关召回、重复片段和上下文超限设计明确行为。

## Security

- 永远不要把 API Key、Access Token、Cookie、私钥、登录文件或真实凭据提交到 Git。
- 密钥使用 Windows Credential Manager、环境变量或其他本机安全存储；共享文件只保留变量名。
- 不要共享整个 `.codex` 或 `.claude` 运行目录；跨设备配置使用环境变量或本地覆盖文件。
- 删除、覆盖、迁移和远程推送前确认精确目标，并优先保留可恢复备份。

## Communication

- 先给出结果，再说明关键改动和验证情况。
- 对不确定事项明确标注假设，不把推测写成事实。
